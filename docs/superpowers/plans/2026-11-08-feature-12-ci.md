**Later change (code review):** the workflow below records the plan; the current file is `.github/workflows/ci.yml`. The review led to these changes:
- **Every push to `main` gets its own concurrency group,** so a burst of pushes never drops a run. Only pull-request runs cancel older ones.
- **`persist-credentials: false` on each checkout,** so no token sits in the checkout the test containers mount.
- **`actions/checkout@v5` and `actions/setup-node@v5`,** because `@v4` runs on a Node runtime GitHub is phasing out. The app still builds with Node 20.
- **The `npm ci` step has a name.**

**Goal (spec section 11, "CI"):** a GitHub Actions workflow that checks pushes to `main` and every pull request with the same commands a developer runs locally:
1. **Backend:** `docker compose run --rm -T lint`, then `docker compose run --rm -T tests`. A lint error fails the job.
2. **Frontend (`web/`):** Node 20, `npm ci`, `npm run build`. The build type-checks with `vue-tsc`, then builds with Vite.
3. **Images:** `docker compose build`, run only after jobs 1 and 2 pass.

**Design choices:**
- **Same commands as locally:** the backend job uses the existing `tests` and `lint` Compose services, so CI and a developer machine can't drift apart. It needs no Python setup on the runner, because everything runs in the `publishing-tests` image.
- **Triggers:**
  - Pushes to `main` and every pull request. Other branches are checked through their pull request, so a push to a branch with an open PR doesn't run CI twice.
  - A newer push to a pull request cancels its older run. Runs on `main` always finish.
- **Timeouts:** 15 minutes per job, instead of GitHub's default of 6 hours.
- **Least privilege:** `permissions: contents: read`; the workflow only reads the code.
- **No secrets needed:** Compose supplies demo defaults for every required setting, and the tests pass their own.
- **Pinned major versions:** `actions/checkout@v4` and `actions/setup-node@v4`. Pinning to a commit SHA would be the production hardening step. The npm cache is keyed on `web/package-lock.json`.

**Tech stack:** GitHub Actions (`ubuntu-latest`, which has Docker and Compose v2), Node 20.

### Task 1: The workflow

**Files:** Create `.github/workflows/ci.yml`

- [ ] **Step 1: Write the workflow.** `.github/workflows/ci.yml`:

```yaml
# Runs the same commands as a developer machine (spec section 11).
name: CI

on:
  # Other branches are checked through their pull request, so nothing runs twice.
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

# A newer push to a pull request cancels its older run; runs on main always finish.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  backend:
    name: Backend lint and tests
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - name: Build the test image
        run: docker compose build tests
      - name: Lint
        run: docker compose run --rm -T lint
      - name: Tests
        run: docker compose run --rm -T tests

  frontend:
    name: Frontend type-check and build
    runs-on: ubuntu-latest
    timeout-minutes: 15
    defaults:
      run:
        working-directory: web
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: web/package-lock.json
      - run: npm ci
      - name: Type-check and build
        run: npm run build

  images:
    name: Docker images
    needs: [backend, frontend]
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - name: Build every service image
        run: docker compose build
```

- **`backend`:** builds the test image first, so the two `run` steps reuse it, then lints and tests.
- **`frontend`:** runs in `web/` (`defaults.run.working-directory`). `npm ci` installs exactly what `package-lock.json` says.
- **`images`:** `needs: [backend, frontend]`, so images are built only once both checks pass. `docker compose build` builds every service outside the `test` profile: `api`, `web`, `source-stub` and `vendor-stub`.

  1. Commit, push the working branch (here `feature-ci`), and open a pull request from it to `main`.
  2. On the pull request's **Checks** tab (or the **Actions** tab), "Backend lint and tests" and "Frontend type-check and build" run side by side and pass.
  3. "Docker images" starts after both and passes.

  **To see the failure path:**
  1. Push one extra commit to the same pull request branch with a deliberate lint error, e.g. an unused import.
  2. The new run starts and cancels the older one.
  3. "Backend lint and tests" fails at "Lint", and "Docker images" is skipped.
  4. Push a commit that removes the error. That way `main` never receives a broken commit.
